# 一、三层分块结构：先建立全局图景
SGEMM 计算 `C(M×N) = A(M×K) × B(K×N)`。GPU 上做矩阵乘的标准思路是**三层切分**，BM/BN/BK 描述的是最外两层：
```
第一层：grid 切分 —— 每个 block 算 C 的一个 BM×BN 大块
第二层：block 内部 —— 每个 thread 算这个大块里的一个 TM×TN 小块
第三层：K 维循环 —— 每次搬 BK 列/行进 shared memory
```
用图表示（BM=64, BN=64, BK=32, TM=TN=4）：
```
C (M×N)                            A (M×K)              B (K×N)
┌────────┬────────┬─────┐          ┌──────────┐
│ block  │ block  │ ... │          │          │ ←──── 每个 K 循环
│ (0,0)  │ (1,0)  │     │          │ 64×32    │       搬一个 BM×BK
├────────┼────────┤     │    =     │ 的 A 块  │       的 A 块和 BK×BN
│ block  │ block  │     │          │ 进 smem  │       的 B 块进 smem
│ (0,1)  │ (1,1)  │     │          └──────────┘
└────────┴────────┴─────┘
   每个 block 负责的 64×64 区域内部：
   ┌────┬────┬────┬────┬────────────┐
   │4×4 │4×4 │4×4 │4×4 │            │  ← 一个 thread 算一个 4×4
   ├────┼────┼────┼────┤   64 列    │    （16 个累加器放寄存器）
   │4×4 │4×4 │ ...   │              │
   └────┴────┴───────┴──────────────┘
      16×16 = 256 个线程 × 各自 4×4 = 64×64
```
## 各参数的含义
| 参数   | 含义                                                              | 值  | 约束                             |
| ------ | ----------------------------------------------------------------- | --- | -------------------------------- |
| **BM** | 一个 block 计算的 C 的**行数**（也是每次搬进 smem 的 A 块的行数） | 64  | BM×TM 相关                       |
| **BN** | 一个 block 计算的 C 的**列数**（也是 B 块的列数）                 | 64  | 决定 block 的 x 维线程数 = BN/TN |
| **BK** | 每次 K 循环搬运的**深度**（A 块的列数、B 块的行数）               | 32  | A 块 = BM×BK，B 块 = BK×BN       |
| **TM** | 单个线程负责的**行数**                                            | 4   | TM×TN = 每线程累加器数           |
| **TN** | 单个线程负责的**列数**                                            | 4   | 通常取 4 的倍数，配合 float4     |
**为什么 K 维要分块？** 如果一次把整行 K 搬进 smem，A 块就是 64×K，K 很大时 smem 装不下（smem 一般只有 48~228KB）。所以沿 K 切成宽 BK 的条带，循环累加：
```
for tile_k in 0..K step BK:
    smem_A ← A[blockRow..+64, tile_k..+32]     # 64×32
    smem_B ← B[tile_k..+32, blockCol..+64]     # 32×64
    __syncthreads()
    用这两块 smem 做部分乘加，累进寄存器里的 sum[4][4]
```

# 二、block 和 grid 为什么这样设置
## block = (16, 16) = 256 线程
由“每个线程算 TM×TN = 4×4”倒推：
```
blockDim.x = BN / TN = 64 / 4 = 16   # x 方向 16 个线程，覆盖 64 列
blockDim.y = BM / TM = 64 / 4 = 16   # y 方向 16 个线程，覆盖 64 行
```
线程 `(tx, ty)` 负责 C 中的这块区域：
```cpp
row0 = blockIdx.y * BM + ty * TM;   // 起始行：先定位 block，再定位线程在大块内的位置
col0 = blockIdx.x * BN + tx * TN;   // 起始列
// 负责 C[row0..row0+4, col0..col0+4]
```
**为什么是 256 而不是更多？** 三个原因：
1. 256 = 8 个 warp，是经典的“好调度”数量；
2. 一个 SM 最多 1024 或 2048 个线程，256/block 意味着一个 SM 能同时塞 **4~8 个 block**，block 之间可以互相切换，隐藏访存延迟；
3. smem 用量：`(64×36 + 32×68)×4B ≈ 15.5KB`，一个 SM（如 100KB smem）能容纳多个 block，occupancy 不受 smem 限制。
## grid = (ceil(N/64), ceil(M/64))
每个 block 算 C 的 64×64，所以需要覆盖整个 C 就要 `(N/64) × (M/64)` 个 block。向上取整是处理 M、N 不是 64 倍数的边缘情况（多余的 block 里的线程会被 `row < M` 的判断挡住，空跑但无害）。

# 三、为什么 padding 能消除 bank conflict（重点）
## 先讲 shared memory 的物理结构
Shared memory 不是一个整块内存，而是 **32 个独立的 bank 并联**，每个 bank 宽 4 字节（一个 float），每个周期每个 bank 只能服务**一个地址**的访问：
```
bank:    0    1    2    3   ...  31
        ┌────┬────┬────┬────┬───┬────┐
word 0  │    │    │    │    │...│    │  ← 地址 0..31 依次分布到 bank 0..31
word 32 │    │    │    │    │...│    │  ← 地址 32 又回到 bank 0
word 64 │    │    │    │    │...│    │
        └────┴────┴────┴────┴───┴────┘
规则：一个 warp 发出 32 个访问请求，如果它们落在不同 bank → 一个周期全部完成
     如果多个线程访问同一 bank 的【不同地址】→ 串行化，N 个冲突就慢 N 倍
     例外：多个线程访问【完全相同的地址】→ 广播，不算冲突
```
**关键公式：`bank = (地址 / 4字节) % 32`，即按 word 下标对 32 取模。**
## 二维数组为什么必然冲突
`a_s[64][36]` 中，第 r 行的起始 word 下标是 `r × 行跨度`。所以：
```
a_s[r][c] 的 bank = (r × stride + c) % 32
```
如果 stride = 32（不 padding，正好 TILE 宽）：
```
a_s[r][c] 的 bank = (r×32 + c) % 32 = c % 32    ← r 完全消失！
```
**每一行都从 bank 0 开始**。看计算循环里读 A 的模式：
```cpp
a_frag[r] = a_s[ty*TM + r][k];   // 所有 tx 读同一地址（广播，OK）
```
一个 warp 里有 2 个不同的 `ty`（warp = tx 0..15, ty 0..1），它们访问：
```
ty=0: a_s[r][k]     → bank = k % 32
ty=1: a_s[r+4][k]   → bank = (4×32 + k) % 32 = k % 32   ← 同一个 bank！
```
地址不同、bank 相同 → **2-way conflict，这次读花 2 个周期**。你原来的代码 block 是 (8,32)，一个 warp 里有 4 个不同的 ty，所以是 **4-way**——等于 smem 吞吐直接砍到 1/4。
## padding 之后发生了什么
stride 从 32 改成 36（`BK + 4`）：
```
a_s[r][c] 的 bank = (r×36 + c) % 32 = (r×4 + c) % 32
                                    ↑↑↑↑
                          每往下一行，起始 bank 偏移 4
```
再验证刚才的冲突场景：
```
ty=0: a_s[r][k]     → bank = (r×4 + k) % 32
ty=1: a_s[r+4][k]   → bank = ((r+4)×4 + k) % 32 = (r×4 + k + 16) % 32
```
两个地址相差 16 个 bank → **不冲突**，一个周期完成。
**为什么 PAD 选 4 而不是 1？** 两个原因：
1. **消冲突**：`36 % 32 = 4 ≠ 0`，任何非 32 倍数的 stride 都行，1 也可以；
2. **保持 16 字节对齐**：一行 = 36 words = 144 字节，`144 % 16 = 0` ✓。如果 PAD=1，一行 = 132 字节，`132 % 16 = 4`，`&a_s[r][0]` 就不再 16 字节对齐，**没法用 float4 向量化读写 shared memory**，编译器会报错或退化成标量。
（补充：132%16=4，其实只有偶数行的起始地址才错位，但只要存在不对齐的 float4 访问就非法。）
## 用具体数字验证加载路径
加载 A 时 8 个线程（一个 quarter-warp，float4 访问按 8 线程一拍处理）写：
```
tid 0..7 → 行 = tid/4（0 或 1），列 = (tid%4)×8（0, 8, 16, 24）
写地址（word 下标）= r×36 + c：
  tid0: 0    tid1: 8    tid2: 16   tid3: 24     ← 行 0
  tid4: 36   tid5: 44   tid6: 52   tid7: 60     ← 行 1
每个线程写一个 float4（4 个连续 word）：
  tid0: bank 0-3    tid4: bank 36%32=4 → bank 4-7
  tid1: bank 8-11   tid5: bank 12-15
  tid2: bank 16-19  tid6: bank 20-23
  tid3: bank 24-27  tid7: bank 28-31
                                        ↑
                          32 个 bank 恰好各被占用一次，零冲突 ✓
```
如果不 pad（stride=32），tid0 和 tid4 都写 bank 0-3 的不同地址 → 2-way 冲突。

# 四、a_lr / a_lk / b_lk / b_lc 是什么
这四个变量解决的问题是：**block 里有 256 个线程，需要合力把 64×32 = 2048 个 float 的 A 块和 32×64 = 2048 个 float 的 B 块搬进 shared memory，怎么分工？**
```
2048 个元素 ÷ 256 个线程 = 每线程搬 8 个（= 两个 float4）
```
## A 块：64 行 × 32 列 → 线程排成 64×4 的搬运矩阵
把 256 个线程想象成 **64 行 × 4 列**的网格，每个线程搬自己那一行的 8 个连续元素：
```
A tile (64×32) 的搬运分工：
列→   0────────8────────16───────24
行0   [tid=0  ][tid=1  ][tid=2  ][tid=3  ]
行1   [tid=4  ][tid=5  ][tid=6  ][tid=7  ]
行2   [tid=8  ][tid=9  ][tid=10 ][tid=11 ]
 ...
行63  [tid=252][tid=253][tid=254][tid=255]
        每格 8 个 float（两个 float4）
```
```cpp
const int a_lr = tid / (BK / 8);        // tid / 4  → 我负责 tile 的第几行（0..63）
const int a_lk = (tid % (BK / 8)) * 8;  // tid % 4 × 8 → 我负责该行的第几列（0/8/16/24）
```
- `BK / 8 = 32 / 8 = 4`：每行需要 4 个线程；
- `tid / 4` 把 tid 映射到行号，`tid % 4` 映射到行内的组号；
- 搬运目标就是 `a_s[a_lr][a_lk .. a_lk+7]`，对应的源是全局内存 `A[block_row + a_lr][tile_k + a_lk .. +7]`。
## B 块：32 行 × 64 列 → 线程排成 32×8 的搬运矩阵
同理，B 块形状不同（矮胖），线程网格也随之变成 **32 行 × 8 列**：
```
B tile (32×64) 的搬运分工：
列→   0────────8────────16───────24───────32───────40───────48───────56
行0   [tid=0 ][tid=1 ][tid=2 ][tid=3 ][tid=4 ][tid=5 ][tid=6 ][tid=7 ]
行1   [tid=8 ]...
 ...
行31  [tid=248] ... [tid=255]
```
```cpp
const int b_lk = tid / (BN / 8);        // tid / 8  → tile 的第几行（0..31，对应 K 方向）
const int b_lc = (tid % (BN / 8)) * 8;  // tid % 8 × 8 → 该行的第几列（0,8,...,56）
```
- `BN / 8 = 64 / 8 = 8`：B 块每行需要 8 个线程；
- 目标 `b_s[b_lk][b_lc .. b_lc+7]`，源 `B[tile_k + b_lk][block_col + b_lc .. +7]`。
## 为什么这个分工方案好
1. **每线程 8 个元素 = 2 条 float4 指令**，保持向量化（如果每线程只搬 1 个 float，就无法用 float4）；
2. **全局内存侧天然合并访存**：同一 warp（tid 连续）搬的是连续内存。比如 tid 0..7 搬 B 的第 0 行的 0..63 列——正好 256 字节连续，一个 warp 的两条 float4 load 完美 coalesced；
3. **shared memory 侧无冲突**：如上一节验证，stride=36 时 bank 恰好错开。
## 注意：计算分工 ≠ 搬运分工
容易混淆的一点——**每个线程“计算哪块”和“搬运哪块”是完全独立的两套映射**：
|          | 计算时                                        | 搬运时                                             |
| -------- | --------------------------------------------- | -------------------------------------------------- |
| 依据     | `(tx, ty)`                                    | 线性 `tid = ty×16 + tx`                            |
| A 的角色 | 读 `a_s[ty×4+r][k]` 参与**自己那 4 行**的累加 | 搬的是 `a_s[tid/4][tid%4×8]`，**跟自己算哪行无关** |
这是有意的：搬运用统一的线性分工保证 coalescing，计算用 (tx,ty) 网格保证数据复用（相邻 4 个 tx 共享同一个 `a_frag`，靠广播免费获得），两者互不干扰，中间用 `__syncthreads()` 做栅栏。

# 五、串起来：一次 K 迭代的完整数据流
```
                     全局内存 (HBM)              寄存器
                    ┌──────────┐
   A[block_row..+64 │ 搬运阶段  │
   , tile_k..+32]   │ 256线程   │    shared memory
          ────────→ │ 每人8个   │ ──────────────→ a_s[64][36]
                    │ float4×2  │
                    │           │
   B[tile_k..+32,   │           │
   block_col..+64]  │           │ ──────────────→ b_s[32][68]
          ────────→ └──────────┘
                          │ __syncthreads()
                          ↓
                    ┌──────────────────────────────┐
                    │ 计算阶段（32 个 k 步）：        │
                    │   a_frag[4] ← a_s[ty*4..][k] │  广播读，无冲突
                    │   bv(float4) ← b_s[k][tx*4]  │  向量读，无冲突
                    │   sum[4][4] += a_frag ⊗ bv   │  16 次 FMA
                    └──────────────────────────────┘
                          │ __syncthreads()
                          ↓
                     下一个 tile_k
```
每个线程每个 k 步用 **8 次 smem 读换 16 次 FMA**（读取/计算比 0.5），而你原来的版本是 5 次读换 4 次 FMA（比值 1.25），这就是寄存器分块提升效率的本质：**累加器越多，同样一份数据被复用得越狠，smem 流量摊得越薄**。

# 六、细节
```
#pragma unroll
for (int r = 0; r < TM; ++r) {
    sum[r][0] = fmaf(a_frag[r], b_vec.x, sum[r][0]);
    sum[r][1] = fmaf(a_frag[r], b_vec.y, sum[r][1]);
    sum[r][2] = fmaf(a_frag[r], b_vec.z, sum[r][2]);
    sum[r][3] = fmaf(a_frag[r], b_vec.w, sum[r][3]);
}
```


`fmaf` 是什么作用？

`fmaf(a, b, c) = a*b + c`，但它是融合乘加（Fused Multiply-Add）：

一条指令完成乘和加（GPU 上通常映射到 FFMA）

只做一次舍入，数值精度通常比先乘再加更好

吞吐也更高，是 GEMM 的标准写法
